# Google Cloud Storage (GCS) Deliverables Runbook
*Document Version: 1.0 • Deliverables Storage & Streaming Protocol • November 2026*

This guide details how Google Cloud Storage stores, secures, and delivers prospecting artifacts (Excel, PDF, CSV) generated by the Michito B2B Engine.

---

## 1. Overview & Bucket Architecture

All generated prospecting deliverables are uploaded to private Google Cloud Storage buckets. End buyers **never** access the bucket directly; instead, the Cloud Run API acts as the secure commercial gateway, streaming files directly to the client's browser upon verifying that the order is marked as `paid`.

### Bucket Topology

```text
gs://michito-staging-deliverables/ (or gs://michito-prod-deliverables/)
└── orders/
    └── {order_id}/
        ├── prospects.xlsx                     # Commercial Deliverable: Formatted Excel spreadsheet
        ├── executive_dossier.pdf              # Commercial Deliverable: PDF Underwriting Report
        ├── prospects.csv                      # Commercial Deliverable: Clean CRM CSV
        ├── executive_dossier.md               # Internal QA: Raw Markdown analysis
        └── prospects_full_intelligence.csv    # Internal QA: Full unmerged scraping logs
```

## 2. Commercial Deliverables vs. Internal Verification Artifacts

| Deliverable Name | File Type | Target Audience | What it Contains |
| :--- | :--- | :--- | :--- |
| **`{order_id}_prospects.xlsx`** | Excel (.xlsx) | Sales & BD Reps | Formatted multi-tab workbook with company overview, executive contacts, decision-maker seniority, intent signals, and 5-touch email/LinkedIn outreach cadences. |

| **`prospects_full_intelligence.csv`** | CSV (.csv) | Internal QA & Engineering | Full audit log containing unmerged public registry responses, raw SMTP logs, and diagnostic scores. Not exposed on the buyer portal. |

## 3. Direct Byte Streaming Protocol

In Cloud Run, static file hosting or generating V4 signed URLs can cause authorization failures if the container's service account lacks `iam.serviceAccounts.signBlob` permissions. 

To eliminate this failure mode, Michito implements **Direct Byte Streaming**:

1. The buyer clicks the download link on the portal:
   `GET /api/v1/orders/{order_id}/download/{file_type}`
2. The endpoint verifies in PostgreSQL that the order status is `paid`. If unpaid, returns `402 Payment Required`.
3. The Cloud Run API uses native Google Cloud IAM credentials to read the blob:
   ```python
   blob = bucket.blob(f"orders/{order_id}/{gcs_filename}")
   file_bytes = blob.download_as_bytes()
   ```
4. Returns a direct HTTP `Response` with `Content-Disposition: attachment; filename="{order_id}_prospects.xlsx"`.
5. The buyer's browser immediately saves the file locally with their order ID prefix.

## 4. Watchdog Safety Guard

If a paid order ever requests a deliverable that cannot be found in the bucket, the endpoint **automatically alerts the engineering team** via Watchdog before returning an error:

```python
app_container.alert_dispatcher.send_alert(
    title="MISSING DELIVERABLE DOWNLOAD ATTEMPT",
    message=f"Buyer attempted to download `{file_type}` for paid order `{order_id}`, but `{gcs_filename}` was not found in bucket `{bucket_name}`.",
    level="error",
    details={"order_id": order_id, "file_type": file_type, "bucket": bucket_name}
)
```

| Setting | Local / Development | Staging (`michito-staging`) | Production (`michito-prod`) |

| **Storage Class** | Standard | Standard Regional (`us-central1`)| Standard Regional (`us-central1`)|
| **Encryption** | None | Google-managed key | Google-managed key |
| **Lifecycle Policy** | N/A | Retain 90 days | Retain 365 days |
